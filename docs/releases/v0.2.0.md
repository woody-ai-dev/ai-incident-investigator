# v0.2.0 — Saved investigations and model usage

AI Incident Investigator now keeps investigation results after a restart and helps
engineers review previous incidents, collection gaps, and model usage in one UI.

## What changed since v0.1.0

- Optional PostgreSQL snapshots preserve the request, evidence, report, creation time,
  execution duration, configured model, and prompt hash. Reads never rerun analysis.
- **Investigations** lists saved reports with service, environment, and creation-date
  filters, cursor pagination, and direct links that survive browser refreshes.
- **Evidence flow** distinguishes collected, partial, empty, disabled, skipped, failed,
  and unrecorded source outcomes, with evidence counts, issues, and collection durations.
- Evidence validation checks selected temporal and metric interpretation constraints.
  New synthetic evaluation cases cover cumulative counters, scrape summaries, heap
  observations, missing context, and lifecycle logs.
- Completed analysis opens **Analysis & checks**. New model prompts request a short
  source-attributed summary; detailed observations stay in findings. Existing long
  summaries remain readable, and empty hypotheses are hidden.
- **Usage** shows 7/30-day UTC token and estimated-cost trends and the five largest
  analyses by tokens, cost, or duration. Cached input is a subset of input, not extra
  tokens. Unknown usage and unsupported pricing remain unknown.
- Provider-reported usage, the actual returned model, duration, and versioned supported
  prices are preserved when available, including for rejected or invalid answers.
  Automatic SDK retries are disabled.
- CI includes PostgreSQL migration tests, Gitleaks secret scanning, and a dynamic
  Python coverage badge. The architecture diagram and setup guides reflect this release.

## Run and upgrade

The default four-service demo still works without PostgreSQL or an API key. To enable
history and usage storage from the checked-out `v0.2.0` source:

```bash
docker compose -f compose.yaml -f compose.persistence.yaml up -d --build --wait --wait-timeout 180
uv sync --locked --dev
uv run --locked python scripts/check_investigation_storage.py
```

The one-shot migration service runs `alembic upgrade head` before application startup.
Existing databases from development snapshots must also be migrated; `0003_llm_usage`
is the current head. Back up any data you need before upgrading. Do not use
`down --volumes` when you want to keep saved investigations.

For a backend run outside Compose, apply migrations using the same `DATABASE_URL` as
the application before restarting it. See the
[persistence guide](https://github.com/woody-ai-dev/ai-incident-investigator/blob/v0.2.0/docs/persistence.md).
Older saved reports remain readable without invented collection outcomes or token usage.
The snapshot and JSON-export schema version stays `1`; it is distinct from app version.
The Java demo service keeps its independent version.

Open **Investigations** and **Usage** in the sidebar. Usage needs saved model calls;
with analysis disabled, it correctly has no model usage. Reading either page is free
of model requests. Live analysis remains an explicit, billable opt-in.

## Scope and limitations

- This is a local demo without authentication, authorization, or an automatic retention
  policy. APIs can still change before `1.0`.
- Investigations start on request. There are no background jobs, autonomous monitoring,
  traces, RAG, automatic fixes, deployments, or on-call notifications.
- Storage is optional. If saving fails, POST returns 503; retrying can repeat a billable
  call. Idempotent submission and recovery of unsaved usage are not implemented.
- Usage totals cover saved application calls, not the provider account or invoice.
  Cost estimates currently support standard-tier text pricing for
  `gpt-4.1-mini-2025-04-14`; other models or tiers can be unpriced.
- Source collection outcomes describe retrieval, not service health. Actuator remains
  a current snapshot; Prometheus counters are cumulative and returned evaluations do
  not prove continuous availability or successful business operations.
- Model conclusions require engineering review. Remaining scrape-wording and temporal
  interpretation issues are documented in the validation records; successful
  structural checks do not verify root cause.
