# Как выпустить v0.1.0 в GitHub

Релиз — это зафиксированная версия кода, тег `v0.1.0` и страница GitHub Release
с описанием возможностей и ограничений. Коммит и push сами по себе релиз
не создают. Этот документ описывает ручную публикацию после проверки MVP.

## 1. Подготовить изменения к pull request

Работай в текущей ветке до завершения проверки. Посмотри изменённые файлы:

```bash
git status --short
git diff --check
git diff
```

В коммит должны попасть код, тесты и публичная документация. Проверь выбранные
файлы в Source Control → Staged Changes и выполни `git diff --cached`.
Приватный `.env`, API-ключи, каталоги кешей, `data/`, `node_modules/` и
результаты тестов добавлять не нужно. Не используй `git add -f` для их включения.

Сначала запусти проверки из разделов README **Checks and CI** и
**Browser end-to-end checks**. Live LLM не является обязательным шагом каждого коммита и
не запускается в обычном CI; результаты ручной проверки сохраняются отдельно.

Добавь проверенные файлы через кнопку **+** в Source Control. Затем посмотри
`git diff --cached --stat`: там должны быть код, тесты, документация и выбранное
демо из `docs/assets/`.

После подготовки индекса:

```bash
git commit -m "feat: prepare evidence-backed investigation MVP"
git push -u origin HEAD
```

Команда `HEAD` отправляет текущую ветку. Перед запуском проверь её имя:

```bash
git branch --show-current
```

## 2. Создать pull request

1. Открой репозиторий `woody-ai-dev/ai-incident-investigator` в GitHub.
2. Перейди **Pull requests → New pull request**.
3. Выбери **base: main**, **compare: свою текущую ветку**.
4. Проверь вкладку **Files changed**: должны быть только изменения этого MVP.
5. Заголовок: `Prepare v0.1.0 investigation MVP`.
6. В описании укажи итоговое поведение, выполненные проверки, ссылку на
   `docs/validation/2026-10-16.md` и оставшиеся ограничения.
7. Нажми **Create pull request**.

Дождись успешного workflow **CI**. В нём должны завершиться четыре задания:
`checks`, `frontend`, `java-demo`, `docker-demo`. Последнее запускается после
трёх остальных. Серый статус или пропущенное задание не равно успешному прогону.
Если проверка упала, открой её лог, исправь причину и отправь новый коммит в
ту же ветку. GitHub обновит PR автоматически.

## 3. Слить проверенный PR

Посмотри финальный diff и результаты проверок. В PR используй
**Squash and merge**, затем **Confirm squash and merge**. Если такой способ
отключён в настройках репозитория, используй разрешённый способ merge.

Открой **Actions → CI** и дождись успешного запуска для нового коммита `main`.
Тег нужно ставить на проверенный коммит `main`, содержащий этот PR.

При желании обнови локальную ветку после merge:

```bash
git switch main
git pull --ff-only origin main
git log -1 --oneline
```

Перед переключением рабочие изменения должны быть закоммичены или сохранены
отдельно. `--ff-only` останавливает pull, если Git пришлось бы создавать merge.

## 4. Подготовить GitHub Release

1. На странице репозитория открой **Releases → Draft a new release**.
2. В **Choose a tag** введи `v0.1.0` и выбери создание нового тега.
3. В **Target** выбери `main`. Сверь текущий SHA этой ветки с успешным
   workflow после merge. Если в `main` появились новые коммиты, дождись их CI
   перед созданием тега.
4. Название релиза: `v0.1.0 — Evidence-backed incident investigation MVP`.
5. Скопируй содержимое `docs/releases/v0.1.0.md` в описание.
6. Проверь ссылки в описании. Шаблон уже ссылается на файлы тега `v0.1.0`;
   они станут доступны после создания этого тега при публикации.
7. Прикрепи готовый файл `docs/assets/mvp-demo.mp4` как release asset.
   Это смонтированная версия на 1:22, около 1,7 МБ, Full HD 16:9 с английскими
   подписями и настоящим ответом модели. Сокращённые паузы обозначены в кадре.
   Полная запись на 1:55 сохранена в `docs/assets/mvp-demo-full.mp4`.
   Оригинальный ответ и его ограничения описаны в `docs/validation/2026-10-16.md`.
8. Для завершённого MVP `v0.1.0` оставь **Set as a pre-release** выключенным.
   Возможность изменения API уже обозначена версией `0.x` и ограничениями
   в описании. При необходимости сохрани через **Save draft** и проверь
   описание до публикации.

Если выпускаешь отдельный тестовый кандидат, используй, например,
`v0.1.0-rc.1` и отметь **Set as a pre-release**. Не создавай тег повторно
в терминале, если создаёшь его через эту форму.

## 5. Опубликовать и проверить

Нажми **Publish release**, когда описание, видео и target готовы.
После публикации проверь страницу релиза, тег, ссылки и возможность открыть
инструкцию запуска на версии `v0.1.0`.

Вкладка **Actions** в текущем проекте запускается для PR и push в `main`;
создание тега само по себе не запускает дополнительную сборку или деплой.
GitHub автоматически прикладывает архив исходников для тега. Docker-образы,
бинарные дистрибутивы и деплой эта публикация не создаёт.

Если после релиза найдена ошибка, исправь её обычным PR и выпусти `v0.1.1`.
Не передвигай опубликованный тег `v0.1.0` на другой коммит.
